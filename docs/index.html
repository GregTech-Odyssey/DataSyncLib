DataSyncLib v26.7.1 for Minecraft 1.20.1

基于注解的 Minecraft Forge 数据同步框架 —— 自动处理客户端-服务器之间的字段同步、变更检测与磁盘持久化。

Minecraft 1.20.1 Forge 47.4.21 Java 21 LGPL 3.0

简介

DataSyncLib 是专为 Minecraft Forge 模组开发设计的数据同步库。通过声明式注解（@SyncToClient、@SyncToServer、@SaveToDisk），自动处理客户端与服务端之间的字段同步、变更检测与磁盘持久化，大幅减少样板代码。

传统 Forge 开发中，你需要手动处理 FriendlyByteBuf 读写、CompoundTag 序列化、以及 getUpdateTag()/saveAdditional() 等方法。DataSyncLib 将这些模式抽象为统一框架 —— 只需在字段上添加注解，继承提供的基类即可。

核心特性

🔁 双向同步

@SyncToClient 和 @SyncToServer 注解自动处理服务端↔客户端字段同步。支持异步调用。

💾 自动持久化

@SaveToDisk 注解标记的字段自动写入/读取 NBT，支持自定义键名、条件保存和默认值排除。

📡 增量同步

内置 dirty flag 机制，仅传输变化的字段。网络格式使用 VarInt 索引寻址，最小化流量。

🔧 可扩展 Codec

统一的 DataSyncCodec 注册表同时支持网络流编解码和持久化数据编解码，预置 30+ 常用类型。

📢 变更通知

通过 listener 回调和 NotifiableHolder 系统，在字段值变化时自动触发业务逻辑。

🧩 开箱即用

提供 FieldDataHolderBlockEntity 基类，继承即可获得完整数据同步和持久化能力。

📦 DataComponent 系统

可选的组件化数据模型，通过 DataComponentRegistry + DataComponentMap 实现类型安全的数据组件存取与合并。

🗂️ Registry 工具

泛型注册表工具类，支持 freeze/unfreeze 生命周期、自动 ID 分配、内置序列化 Codec。

⚡ MethodHandle 反射

全框架使用 MethodHandle + VarHandle 替代传统反射，字段 getter/setter 调用接近原生字节码速度。

📊 FastUtil 集合

全面采用 FastUtil 高性能集合库：Reference2ReferenceOpenHashMap、ReferenceArrayList 等，避免基本类型装箱开销。

🗜️ Data 类型系统

19 种类型的二进制 Data 系统替代 NBT/Tag，VarInt 变长编码，比 Tag 更紧凑高效，支持更多 Map/Collection 类型。

🧠 多级缓存

类级元数据 ConcurrentHashMap 缓存、IdentityHashMapCache、Enum/Array Codec 自动生成缓存，消除重复反射和查找。

快速开始

1. 添加依赖

// build.gradle
dependencies {
    implementation 'com.gto:datasynclib:26.7.1'
}

2. 创建 BlockEntity

public class MyBlockEntity extends FieldDataHolderBlockEntity {

    @SyncToClient
    @SaveToDisk
    private int energy = 0;

    @SyncToServer
    private boolean active = false;

    public MyBlockEntity(BlockPos pos, BlockState state) {
        super(ModBlockEntities.MY_BLOCK_ENTITY.get(), pos, state);
    }

    public void serverTick(ServerLevel level) {
        // 修改字段值
        energy++;
        setChanged();  // 标记需要保存到磁盘
        DataSyncNetwork.syncBlockEntityToClient(this, false, true);
    }
}
继承 FieldDataHolderBlockEntity 后，框架自动处理 getUpdateTag() / saveAdditional() / load() 的序列化逻辑。

整体架构

DataSyncLib 采用分层架构：

层次组件职责
注解层@SyncToClient, @SyncToServer, @SaveToDisk 等声明式标记字段的同步和持久化行为
元数据层FieldDefinitionStorage, FieldAnnotationMetadata扫描和缓存类级别的字段定义元数据，含字段工厂、Codec、Strategy
定义层DataFieldDefinition<T>封装单个字段的反射信息、getter/setter、序列化方法、条件判断
管理层FieldDataManager, LazyFieldDataManager每实例生命周期管理：变更检测、序列化、反序列化，含重入保护
字段层DataField, BooleanField, IntField, ObjCodecField…单个字段的读写、变化检测、缓冲区序列化的具体实现
访问层CollectionAccess, MapAccess, SerializableAccess…对 final 字段（集合/Map/自定义类型）的代理访问与序列化
编解码层DataSyncCodec, ByteStreamCodec, DataCodec类型级别的编解码器注册与调用，统一网络和持久化
传输层DataSyncNetwork, BlockEntitySyncPacket, EntitySyncPacket网络包发送与接收，支持 BlockEntity 和 Entity 的 C2S/S2C 双向通信

同步与持久化流程

网络同步流程

字段同步需要 主动调用 DataSyncNetwork 的静态方法触发。框架不会自动在每 tick 推送数据。

  1. 修改字段值 — 在 tick 或业务方法中修改被注解标记的字段
  2. 调用同步方法 — 调用 DataSyncNetwork.syncBlockEntityToClient(be, forceAll, auto)（服务端）或 syncBlockEntityToServer(be, forceAll, auto)（客户端）
  3. 内部流程 — 同步方法内部调用 FieldDataManager.updateFieldDirtyFlags() 检测变化 → writeToNetworkBuffer() 序列化 → 发送网络包
  4. 远端接收 — 收到包后调用 FieldDataManager.readFromNetworkBuffer() 反序列化，还原字段值
  5. 更新通知 — 若字段设置了 notifyUpdate = true，调用 scheduleUpdate() 通知渲染刷新
异步支持：所有 DataSyncNetwork 的发送方法都支持异步调用。方法内部检测到变化后，通过 level.getServer().execute() 或 Minecraft.getInstance().execute() 将实际网络发送调度到主线程。

持久化流程

  1. 调用 setChanged() — 当数据发生变化时，必须调用 BlockEntity 的 setChanged() 标记区块需要保存
  2. Minecraft 保存区块 — 原版保存机制触发 saveAdditional()，框架自动将 @SaveToDisk 字段序列化为 NBT
  3. 加载恢复 — 区块加载时，load() 方法自动恢复持久化的字段值
重要：框架不会自动调用 setChanged()。你必须在数据变更后手动调用 setChanged()，否则区块不会被标记为脏，数据不会写入磁盘。

autoUpdate 与 markFieldsForSync

@SyncToClient 和 @SyncToServer 的 autoUpdate 属性（默认 true）：

  • autoUpdate = true — 每次调用 updateFieldDirtyFlags() 时自动调用 detectChange() 对比新旧值。适合基本类型和简单对象
  • autoUpdate = false — 不会自动检测变化。必须手动调用 markFieldsForSync("fieldName") 标记为脏，下一次同步时才会推送。适合需要精确控制同步时机的场景

markFieldsForSync 方法就是专门为 autoUpdate = false 的字段设计的 —— 当设置为 false 时，即使字段值变了，框架也不会自动检测到，必须手动标记。

高性能设计

DataSyncLib 在每一层都针对性能做了优化，从字段访问到序列化格式再到集合选择，确保在高频 tick 场景下最小化性能开销。

MethodHandle 替代传统反射

框架完全不使用 Field.get() / Field.set() 等传统反射 API。所有字段访问通过 MethodHandle 和 VarHandle 实现：

  • ReflectUtil.createAdaptedGetter() — 创建签名为 (Object) → fieldType 的 MethodHandle，通过 invokeExact 调用
  • ReflectUtil.createAdaptedSetter() — 创建签名为 (Object, fieldType) → void 的 MethodHandle
  • 精确类型匹配 — 所有 MethodHandle 通过 asType() 适配为精确签名，支持 invokeExact（比 invoke 更快）
  • 优于传统反射 — MethodHandle 经过 JIT 编译后可内联，性能接近直接字段访问，远超 Field.get/set
  • 访问权限绕过 — 通过 MethodHandles.privateLookupIn() 获取私有字段的访问权限，无需反复 setAccessible

FastUtil 高性能集合

框架全面使用 FastUtil 库替代 Java 标准集合：

FastUtil 类型使用场景优势
Reference2ReferenceOpenHashMapDataSyncCodec 注册表、FieldDataManager 字段表、FieldDefinitionStorage 策略表基于 identityHashCode 的键查找，避免 equals() 碰撞；开放寻址法内存连续
ReferenceArrayListRegistry 的 idValues 列表基于 identity 的 ArrayList，避免 equals 调用
Reference2ReferenceLinkedOpenHashMapRegistry.IdMapidentity 键 + 保留插入顺序
Object2IntMap / Object2LongMapFieldAccess 代理集合的哈希图避免 Integer/Long 装箱，节省内存和 GC 压力
IntCollection / LongCollectionFieldAccess 代理集合基本类型集合接口，无装箱开销
Int2IntMap / Long2LongMap 等DataComponentKey Builder 方法（100+）覆盖所有基本类型组合的 Map，零装箱

FastUtil 的关键优势：

  • 节省内存 — 基本类型专用集合无装箱对象，内存占用降低 3-5 倍
  • 减少 GC — 不产生短生命周期的 Integer/Long 等包装对象
  • 更好的缓存局部性 — 开放寻址哈希表中键和值存储在连续数组中，CPU 缓存友好
  • 自定义哈希策略 — 支持 Hash.Strategy 接口定制等值和哈希逻辑（如 ItemStack 的忽略 NBT 比较）

多级缓存体系

框架在多个层级实现了缓存，避免重复的反射扫描和 Codec 查找：

缓存层实现缓存内容
类级元数据ConcurrentHashMap<Class, FieldDefinitionStorage>每个类的所有被注解字段定义（含父类继承），首次访问后永久缓存
字段工厂IdentityHashMapCache<Class, Factory>类型到 DataField 工厂的映射，基于 identity 键
泛型工厂HashMapCache<Supplier, Factory>泛型类型参数到工厂的映射
Codec 注册表Reference2ReferenceOpenHashMap类型到 DataSyncCodec 的直接映射，O(1) identity 查找

MethodHandleDataFieldDefinition 字段级getter/setter/condition/listener 的 MethodHandle 在构造时一次性解析

其他性能优化

  • 双检锁延迟初始化 — LazyFieldDataManager 使用 double-checked locking，FieldDataManager 仅在首次使用时创建
  • volatile 重入保护 — FieldDataManager.updating 和 writing 标志用 volatile 实现无锁重入保护
  • 直接数组访问 — AbstractDataComponentMap 直接操作 FastUtil 内部 key[] 和 value[] 数组，绕过标准 Map API 的方法调用开销
  • VarInt 索引寻址 — 网络协议使用 VarInt 字段索引（而非字段名字符串），减少传输字节数
  • 增量同步 — dirty flag 机制确保仅传输变化的字段，空闲时零网络开销
  • 预排序字段数组 — FieldDataManager 内部维护 syncToClientFields[] 等预排序数组，避免每次同步时遍历所有字段

IDataSerializable 接口

当字段类型实现 IDataSerializable 时，框架通过 SerializableAccess 代理其序列化。提供完整的变化追踪和双通道序列化：

方法说明
detectChange()检测数据是否变化（对比快照或标记）。autoUpdate=true 时每轮同步调用
markAsChanged()强制标记为已变化，确保纳入下次同步
clearChanged()清除变化标记（同步/持久化完成后调用）
isChanged()检查是否已标记为变化
writeBuffer(side, buf)将数据写入 FriendlyByteBuf（网络同步）
readBuffer(side, buf)从 FriendlyByteBuf 读取数据（网络同步）
writeData()将数据编码为 Data 对象（磁盘持久化）
readData(data, dataVersion)从 Data 对象解码数据，含版本号用于数据迁移（磁盘持久化）

AbstractDataSerializable 提供便捷基类，默认使用 boolean 标记追踪变化。需要复杂变化检测（如对比快照）的子类可重写 detectChange()。

DataField 接口

DataField<T> 定义单个被管理字段的操作接口。每个被注解标记的字段对应一个 DataField 实现实例，是字段值读写和序列化的执行单元。

方法说明
getDefinition()返回字段的 DataFieldDefinition 元数据
markAsChanged(source)标记该字段为脏（针对特定 source 对象）
isChanged(source)检查字段是否已标记为脏
clearChanged(source)清除脏标记
detectChange(side, source, auto)检测字段值是否发生变化，auto 参数指示是否为自动检测模式
writeToBuffer(side, source, buf, force)将字段值写入网络缓冲区。force=true 时忽略脏标记强制写入
readFromBuffer(side, source, buf)从网络缓冲区读取并设置字段值，同时触发 listener 回调
writeToData(source)将字段值编码为 Data 对象用于持久化
readFromData(source, data, version)从 Data 对象解码并还原字段值
mustDetect()default false。返回 true 时即使未标记为脏也会调用 detectChange

还定义了内部接口 Factory<T>、CustomFactory<T>、CustomGenericFactory<T> 用于插件化的工厂注册系统。

DataFieldDefinition

DataFieldDefinition<T> 封装单个被管理字段的完整元数据和行为。由 FieldDefinitionStorage 在类扫描时创建，包含：

  • 反射信息 — Field、isFinal、genericType[]、genericCodecs[]
  • 访问器 — 通过 MethodHandle.invokeExact() 实现高性能 getter/setter（覆盖所有基本类型 + Object），构造时一次性解析，运行时接近原生字段访问速度
  • 序列化代理 — 支持 Codec 注解指定的自定义序列化方法（也通过 MethodHandle 调用），或自动从 DataSyncCodec 查找
  • 条件判断 — skipSync() / skipSave() 系列方法，通过 MethodHandle 调用，支持所有基本类型的方法分派
  • 变化策略 — FastUtil Hash.Strategy 用于变化检测，默认 OBJECT_STRATEGY（hashCode/equals）
  • 默认值 — 支持 defaultValue 字符串解析和 defaultValueGetter MethodHandle 引用
  • 监听器 — getListener(side) 返回字段更新时的回调 MethodHandle，通过 invokeExact 调用

FieldDataManager

FieldDataManager 是每个 IFieldDataHolder 实例的核心管理器，负责被注解字段的完整生命周期。

核心职责

  • 字段发现与实例化 — 从 FieldDefinitionStorage 读取类级元数据，为每个字段创建 DataField 实现
  • 变更检测 — updateFieldDirtyFlags(LogicalSide, boolean auto) 遍历同步字段，调用 detectChange
  • 网络序列化 — 先写自定义同步数据，然后按 (VarInt fieldIndex, fieldPayload) 格式写入每个脏字段
  • 数据持久化 — 通过 writeToData()/readFromData() 使用 StringMapData 格式读写
  • 重入保护 — updating 和 writing volatile 标志防止递归
  • 定向字段管理 — 内部维护 syncToClientFields[]、syncToServerFields[]、saveFields[] 三个独立数组

主要方法

方法说明
updateFieldDirtyFlags(side, auto)遍历同步字段调用 detectChange。有变化或已标记脏则返回 true
writeToNetworkBuffer(side, force)序列化脏字段为 byte[]。force=true 时写入所有字段
readFromNetworkBuffer(side, data)反序列化 byte[] 并还原字段值，触发 listener 和 scheduleUpdate
writeToData()序列化所有 @SaveToDisk 字段为 StringMapData
readFromData(data, dataVersion)从 StringMapData 反序列化还原所有持久化字段
markFieldsForSync(fields...)按 DataFieldDefinition 或字段名字符串标记为脏
hasSyncFields(side) / hasSaveFields()查询是否有对应类型的被管理字段

LazyFieldDataManager

线程安全的 FieldDataManager 延迟初始化包装器。使用双重检查锁定（double-checked locking）确保 FieldDataManager 仅创建一次，减少不需要时的开销。

public class MyHolder implements IFieldDataHolder {
    private final LazyFieldDataManager fieldDataManager =
        new LazyFieldDataManager(this);

    @Override
    public FieldDataManager getFieldDataManager() {
        return fieldDataManager.get();
    }
}

FieldDefinitionStorage

类级别的字段元数据中心注册表。首次访问某个类时扫描其所有字段，缓存到 ConcurrentHashMap 中。支持父类继承 —— 子类自动继承父类的字段定义。

registerInterfaceFactory(type, factory, priority)接口匹配，如 IDataSerializable → SerializableAccess
registerCustomFactory(predicate, factory, priority)自定义谓词匹配，按 priority 降序尝试
registerGenericFactory(type, factory, genericTypes)泛型类型匹配，如 Map<String, Integer>
registerCustomGenericFactory(predicate, factory, priority)自定义泛型谓词匹配
registerAccessFactory / registerAccessInterfaceFactory注册 final 字段的 Access 代理工厂
registerStrategy(type, strategy)注册类型的 Hash.Strategy 用于变化检测

异步原理：方法内部检测变化并序列化数据后，通过 level.getServer().execute()（服务端）或 Minecraft.getInstance().execute()（客户端）将网络包发送调度到主线程，因此本身可在任意线程调用。另外，当数据由服务端→客户端同步时，接收方的 handler 会自动对 BlockEntity 调用 be.setChanged()。

DataSyncCodec 编解码系统

DataSyncCodec<T> 将网络流编解码器和持久化数据编解码器配对为统一单元。每个 Codec 含四个函数式组件：

组件类型用途
streamWriterByteStreamEncoder<T>写入 FriendlyByteBuf（网络同步）
streamReaderByteStreamDecoder<T>从 FriendlyByteBuf 读取（网络同步）
dataWriterDataEncoder<T>编码为 Data 对象（持久化）
dataReaderDataDecoder<T>从 Data 对象解码（持久化）

特性：

  • FastUtil 注册表 — 内部使用 Reference2ReferenceOpenHashMap 存储类型到 Codec 的映射，基于 identity 键的 O(1) 查找
  • 多来源构造 — of(streamCodec) / of(dataCodec) / of(streamCodec, dataCodec) / of(streamCodec, mojangCodec)
  • 枚举自动生成 — 所有 enum 类型首次访问时通过 ConcurrentHashMapCache 自动生成并缓存 Codec
  • 数组自动生成 — 所有非基本类型数组首次访问时通过 ConcurrentHashMapCache 自动生成并缓存 Codec
  • 泛型支持 — register() 可接受 Class<?>... genericTypes 参数，内部用 identityHashCode 包装数组作为缓存键
  • Minecraft 集成 — 提供 register(type, Registry) 便捷方法，自动从 Minecraft 注册表创建 Codec

DataComponent 系统

DataComponent 系统提供了一种可选的组件化数据模型，类似于 Minecraft 原版的 DataComponent。通过 DataComponentRegistry 管理带类型的 Key，用 DataComponentMap 存储数据，支持高效的合并语义。

DataComponentRegistry

继承 Registry<String, DataComponentKey<?>>，同时实现了 ByteStreamCodec<DataComponentMap>、DataCodec<DataComponentMap> 和 Mojang Codec<DataComponentMap>，可直接作为三种序列化通道的编解码器使用。

// 创建注册表
DataComponentRegistry registry = new DataComponentRegistry("my_mod");
registry.unfreeze();

// 注册组件 Key —— 方式一：直接传 Codec
var ENERGY = registry.register("energy", DataSyncCodec.INT_CODEC);

// 注册组件 Key —— 方式二：Builder 模式（含合并/创建函数）
var ITEMS = registry.register("items", DataComponentKey
    .collectionBuilder((ArrayList<ItemStack> c) -> new ArrayList<>(c))
    .andThen(b -> b.codec(DataSyncCodec.ITEM_STACK_CODEC)));

registry.freeze();

DataComponentKey<T>

组件键，基于 identityHashCode 进行恒等查找。核心字段：

  • name — 组件名称
  • codec — DataSyncCodec，为 null 时该 Key 不参与直接序列化（但仍可参与合并）
  • mixCode — System.identityHashCode(this) 混合后的哈希值，用于恒等键查找
  • mergeFunction(T oldVal, T newVal) → T — 合并策略（如集合取并集，Map 做 putAll）
  • createFunction(T val) → T — 存储前转换（如创建防御性副本）

提供 100+ 静态 Builder 工厂方法覆盖 FastUtil 所有集合和 Map 类型的合并/创建策略。

DataComponentMap

继承 AbstractDataComponentMap，基于恒等键的自定义哈希表。提供类型安全的访问方法：

DataComponentMap map = new DataComponentMap();
map.put(ENERGY, 1000);

// 类型安全访问
int e = map.getInt(ENERGY);         // 不存在返回 0
Integer e2 = map.getData(ENERGY);    // 不存在返回 null
boolean has = map.containsKey(ENERGY);

// 高级操作
map.getOrCreateData(ITEMS, ArrayList::new);  // 惰性创建
map.getOrPut(ENERGY, 500);                // 不存在则放入
map.merge(ENERGY, 200);                     // 使用 Key 的 mergeFunction 合并
map.merge(otherMap);                           // 批量合并另一个 map

还提供了 getBoolean、getLong、getString 等类型便捷方法，Key 不存在时返回安全默认值。

AbstractDataComponentMap

自定义 identity-based 哈希表基类，重写 Reference2ObjectOpenHashMap 的 get/put/containsKey 以使用 DataComponentKey.mixCode（基于 System.identityHashCode 混合后的哈希值）和 == 恒等比较。关键性能特征：

  • 恒等键查找 — 不同 Registry 中同名 Key 具有不同 identity，避免命名冲突和 equals 开销
  • 直接内部数组访问 — 绕过 FastUtil 标准 API，直接操作 key[] 和 value[] 内部数组，消除方法调用开销
  • 预计算 mixCode — DataComponentKey 在构造时通过 HashCommon.mix(System.identityHashCode(this)) 预计算哈希值，查找时无需重复计算
  • 开放寻址法 — 线性探测解决哈希冲突，内存连续且 CPU 缓存友好

Registry 工具类

Registry<K extends Comparable<K>, V> 是一个泛型注册表工具类，将可比较的键映射到值，并自动分配整数 ID。

BlockEntity 用法（推荐）

参考 TestBlockEntity（位于 com.gto.datasynclib.test）获取完整示例。

public class MyMachineBlockEntity extends FieldDataHolderBlockEntity {

    @SyncToClient(notifyUpdate = true)
    @SaveToDisk
    private int progress;

    @SyncToClient
    @SaveToDisk(defaultValue = "0")
    private int maxProgress = 100;

    @SyncToServer
    private boolean redstoneMode;

    @SaveToDisk
    private final ItemStack[] inventory = new ItemStack[9];

    public MyMachineBlockEntity(BlockPos pos, BlockState state) {
        super(ModBlockEntities.MY_MACHINE.get(), pos, state);
    }

    // 服务端 tick（需在 Block 的 getTicker 中绑定）
    public void serverTick(ServerLevel level) {
        if (progress < maxProgress) {
            progress++;
            setChanged();  // ★ 标记需要保存到磁盘
        }
        // 每 20 tick 同步一次到客户端
        if (level.getGameTime() % 20 == 0) {
            DataSyncNetwork.syncBlockEntityToClient(this, false, true);
        }
    }

    // 客户端 tick
    public void clientTick() {
        if (level.getGameTime() % 20 == 0) {
            // 将 redstoneMode 的改变发送到服务端
            DataSyncNetwork.syncBlockEntityToServer(this, false, true);
        }
    }
}

自动同步详解

网络同步需要两步配合：

  1. 注解配置 — 字段上设置 autoUpdate = true（默认）时，框架自动对比新旧值检测变化；设为 false 时需要手动 markFieldsForSync("fieldName")
  2. 主动触发同步 — 调用 DataSyncNetwork.syncBlockEntityToClient(be, forceAll, auto) 方法触发实际的网络发送
// autoUpdate = true（默认）—— 自动检测变化
@SyncToClient
private int energy;

public void serverTick(ServerLevel level) {
    energy += 10;  // 直接修改，框架会自动检测到变化
    if (level.getGameTime() % 20 == 0) {
        DataSyncNetwork.syncBlockEntityToClient(this, false, true);
        // ↑ auto=true: 内部调用 updateFieldDirtyFlags(LogicalSide.SERVER, true)
        //    detectChange 自动发现 energy 变化 → 纳入同步
    }
}
// autoUpdate = false —— 需要手动标记
@SyncToClient(autoUpdate = false)
private int energy;

public void setEnergy(int value) {
    this.energy = value;
    markFieldsForSync("energy");  // ★ 必须手动标记
}

持久化详解

持久化依赖 Minecraft 原版的区块保存机制：

  1. 标记脏区块 — 数据变更后调用 setChanged()
  2. Minecraft 自动保存 — 原版每隔一段时间检查脏区块并调用 saveAdditional()
  3. 框架序列化 — FieldDataHolderBlockEntity.saveAdditional() 自动调用 writeToData()
关键：不调用 setChanged()，数据不会写入磁盘。建议在修改任何 @SaveToDisk 字段后立即调用。

注册自定义 Codec

// 方式一：分别指定四个编解码器

    MyCustomType.class,
    (buf, obj) -> buf.writeInt(obj.getValue()),              // streamWriter
    buf -> new MyCustomType(buf.readInt()),                   // streamReader
    obj -> IntData.valueOf(obj.getValue()),                 // dataWriter
    (data, version) -> new MyCustomType(data.getInt())        // dataReader
);

    ByteStreamCodec.of(myWriter, myReader),
    DataCodec.of(myDataWriter, myDataReader)
);

// 方式三：使用 ByteStreamCodec + Mojang Codec
DataSyncCodec.register(MyCustomType.class,
    ByteStreamCodec.of(myWriter, myReader),

// 方式四：从 Forge Registry 创建
DataSyncCodec.register(MyMobEffect.class, BuiltInRegistries.MOB_EFFECT);
