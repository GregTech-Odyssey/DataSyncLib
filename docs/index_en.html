DataSyncLib v26.7.1 for Minecraft 1.20.1

An annotation-driven Minecraft Forge data synchronization framework — automatic client-server field sync, change detection, and disk persistence.

Minecraft 1.20.1 Forge 47.4.21 Java 21 LGPL 3.0

Introduction

DataSyncLib is a data synchronization library purpose-built for Minecraft Forge mod development. Using declarative annotations (@SyncToClient, @SyncToServer, @SaveToDisk), it automates field synchronization between client and server, change detection, and disk persistence — drastically reducing boilerplate code.

In traditional Forge development, you must manually handle FriendlyByteBuf reading/writing, CompoundTag serialization, and methods like getUpdateTag()/saveAdditional(). DataSyncLib abstracts these patterns into a unified framework — just annotate your fields and extend the provided base class.

Key Features

🔁 Bidirectional Sync

@SyncToClient and @SyncToServer handle server↔client field synchronization automatically. Async-safe.

💾 Auto Persistence

@SaveToDisk fields are automatically written to/read from NBT, with custom keys, conditional saves, and default-value exclusion.

📡 Incremental Sync

Built-in dirty flag mechanism transmits only changed fields. VarInt index-addressed wire format minimizes bandwidth.

🔧 Extensible Codec

Unified DataSyncCodec registry supporting both stream codecs and data codecs. 30+ pre-registered types.

📢 Change Notification

listener callbacks and NotifiableHolder system trigger business logic on field value changes.

🧩 Ready to Use

Extend FieldDataHolderBlockEntity to get full sync and persistence capabilities out of the box.

📦 DataComponent System

Optional component-based data model via DataComponentRegistry + DataComponentMap with type-safe access and merging.

🗂️ Registry Utility

Generic registry with freeze/unfreeze lifecycle, automatic integer ID assignment, and built-in serialization codecs.

⚡ MethodHandle Reflection

MethodHandle + VarHandle throughout, replacing traditional reflection. Field access approaches native bytecode speed.

📊 FastUtil Collections

Extensive use of FastUtil high-performance collections — Reference2ReferenceOpenHashMap, ReferenceArrayList, etc. — eliminating boxing overhead.

🗜️ Data Type System

Custom 19-type binary Data system replacing NBT/Tag. VarInt variable-length encoding, more compact and efficient than Tag.

🧠 Multi-Level Caching

Class-level ConcurrentHashMap metadata cache, IdentityHashMapCache, Enum/Array codec auto-generation cache — no repeated reflection scans.

Quick Start

1. Add Dependency

// build.gradle
dependencies {
    implementation 'com.gto:datasynclib:26.7.1'
}

2. Create a BlockEntity

public class MyBlockEntity extends FieldDataHolderBlockEntity {

    @SyncToClient
    @SaveToDisk
    private int energy = 0;

    @SyncToServer
    private boolean active = false;

    public MyBlockEntity(BlockPos pos, BlockState state) {
        super(ModBlockEntities.MY_BLOCK_ENTITY.get(), pos, state);
    }

    public void serverTick(ServerLevel level) {
        energy++;
        setChanged();  // Mark chunk for saving to disk
        DataSyncNetwork.syncBlockEntityToClient(this, false, true);
    }
}
When extending FieldDataHolderBlockEntity, the framework automatically handles serialization in getUpdateTag() / saveAdditional() / load().

Sync & Persistence Flow

Network Sync Flow

Field synchronization requires explicit calls to DataSyncNetwork static methods. The framework does not push data automatically on every tick.

  1. Modify field values — change annotated fields in tick or business methods
  2. Call sync method — invoke DataSyncNetwork.syncBlockEntityToClient(be, writeAll, autoOnly) (server side) or syncBlockEntityToServer(be, writeAll, autoOnly) (client side)
  3. Internal pipeline — the method internally calls FieldDataManager.updateFieldDirtyFlags() → writeToNetworkBuffer() → sends network packet
  4. Remote reception — the packet triggers FieldDataManager.readFromNetworkBuffer() to deserialize and restore field values
  5. Update notification — if the field has notifyUpdate = true, scheduleUpdate() is called to notify UI refresh
Async support: all DataSyncNetwork send methods are async-safe. After detecting changes and serializing, they dispatch network sends to the main thread via level.getServer().execute() (server) or Minecraft.getInstance().execute() (client).

Persistence Flow

  1. Call setChanged() — when data changes, you must call the BlockEntity's setChanged() to mark the chunk as needing save
  2. Minecraft saves the chunk — vanilla save mechanics trigger saveAdditional(), where the framework serializes @SaveToDisk fields to NBT
  3. Load restoration — on chunk load, load() automatically restores persisted field values
Important: the framework does not call setChanged() for you. You must call it manually after data changes, otherwise the chunk is not marked dirty and data won't be written to disk.

autoUpdate and markFieldsForSync

The autoUpdate attribute on @SyncToClient and @SyncToServer (default true):

  • autoUpdate = true — detectChange() is called automatically each time updateFieldDirtyFlags() runs. Best for primitives and simple objects.
  • autoUpdate = false — no automatic change detection. You must manually call markFieldsForSync("fieldName") to mark it dirty, after which the next sync push will include it. Best when you need precise control over sync timing.

The markFieldsForSync method is designed specifically for autoUpdate = false fields — even if the value changes, the framework won't detect it automatically; a manual mark is required.

Performance Design

DataSyncLib is optimized at every layer — from field access to serialization format to collection selection — ensuring minimal overhead in high-frequency tick scenarios.

MethodHandle Instead of Reflection

The framework completely avoids traditional reflection APIs like Field.get() / Field.set(). All field access is implemented via MethodHandle and VarHandle:

  • ReflectUtil.createAdaptedGetter() — creates a (Object) → fieldType MethodHandle, invoked via invokeExact
  • ReflectUtil.createAdaptedSetter() — creates a (Object, fieldType) → void MethodHandle
  • Exact type matching — all MethodHandles are adapted to exact signatures via asType(), enabling invokeExact (faster than invoke)
  • Superior to reflection — MethodHandles can be inlined after JIT compilation, approaching direct field access speed, far exceeding Field.get/set
  • Private access — uses MethodHandles.privateLookupIn() to obtain private field access without repeated setAccessible calls

FastUtil High-Performance Collections

The framework uses FastUtil collections throughout — 57 usages across 29 source files:

Key FastUtil advantages:

  • Memory savings — primitive-specialized collections avoid wrapper objects, 3-5x smaller footprint
  • Reduced GC — no short-lived Integer/Long wrappers generated
  • Better cache locality — open-addressing hash tables store keys and values in contiguous arrays, CPU-cache-friendly
  • Custom hashing — Hash.Strategy interface enables custom equality and hashing (e.g. ItemStack comparison ignoring NBT)

Multi-Level Caching

The framework implements caching at multiple levels to avoid repeated reflection scans and codec lookups:

Additional Optimizations

  • Double-checked locking — LazyFieldDataManager uses DCL; FieldDataManager is created only on first use
  • volatile re-entrancy guards — FieldDataManager.updating and writing flags use volatile for lock-free re-entrancy protection
  • Direct array access — AbstractDataComponentMap directly operates on FastUtil internal key[] and value[] arrays, bypassing standard Map API call overhead
  • VarInt index addressing — network protocol uses VarInt field indices (not field name strings), reducing transmitted bytes
  • Incremental sync — dirty flag mechanism ensures only changed fields are transmitted; zero network overhead when idle
  • Pre-sorted field arrays — FieldDataManager maintains pre-sorted syncToClientFields[] etc., avoiding per-sync iteration over all fields

DataFieldDefinition

DataFieldDefinition<T> encapsulates the complete metadata and behavior for a single managed field. Created by FieldDefinitionStorage during class scanning:

  • Reflection info — Field, isFinal, genericType[], genericCodecs[]
  • Accessors — high-performance getters/setters via MethodHandle.invokeExact() (covering all primitives + Object), resolved once at construction time, approaching native field access speed
  • Serialization proxy — supports custom serialization methods specified via @Codec annotation (also invoked via MethodHandle), or auto-lookup from DataSyncCodec
  • Condition checks — skipSync() / skipSave() method families, called via MethodHandle, supporting all primitive type method dispatch
  • Change strategy — FastUtil Hash.Strategy for change detection, defaulting to OBJECT_STRATEGY (hashCode/equals)
  • Default values — supports defaultValue string parsing and defaultValueGetter MethodHandle references
  • Listeners — getListener(side) returns callback MethodHandle invoked via invokeExact on field update

FieldDataManager

FieldDataManager is the per-instance core manager for each IFieldDataHolder, responsible for the full lifecycle of annotated fields.

Core Responsibilities

  • Field discovery & instantiation — reads class-level metadata from FieldDefinitionStorage, creates DataField implementations for each field
  • Change detection — updateFieldDirtyFlags(LogicalSide, boolean autoOnly) iterates sync fields, calling detectChange
  • Network serialization — writes custom sync data first, then each dirty field as (VarInt fieldIndex, fieldPayload) pairs
  • Data persistence — via writeToData()/readFromData() using the StringMapData format
  • Re-entrancy protection — updating and writing volatile flags prevent recursion
  • Directional field management — maintains three independent arrays: syncToClientFields[], syncToServerFields[], saveFields[]

Key Methods

MethodDescription
updateFieldDirtyFlags(side, autoOnly)Iterates sync fields calling detectChange. Returns true if any change or dirty flag found
writeToNetworkBuffer(side, writeAll)Serializes dirty fields to byte[]. writeAll=true writes all fields
readFromNetworkBuffer(side, data)Deserializes byte[] and restores field values, triggers listener and scheduleUpdate
writeToData()Serializes all @SaveToDisk fields to StringMapData
readFromData(data, dataVersion)Deserializes and restores all persisted fields from StringMapData
markFieldsForSync(fields...)Marks fields as dirty by DataFieldDefinition or field name string
hasSyncFields(side) / hasSaveFields()Query whether managed fields of the given type exist

LazyFieldDataManager

A thread-safe, lazy-initializing wrapper for FieldDataManager. Uses the double-checked locking pattern to ensure FieldDataManager is created only once, reducing overhead when not needed.

public class MyHolder implements IFieldDataHolder {
    private final LazyFieldDataManager fieldDataManager =
        new LazyFieldDataManager(this);

    @Override
    public FieldDataManager getFieldDataManager() {
        return fieldDataManager.get();
    }
}

DataSyncCodec System

DataSyncCodec<T> pairs a network stream codec with a persistent data codec into a single unit. Each codec contains four functional components:

ComponentTypePurpose
streamWriterByteStreamEncoder<T>Write objects to FriendlyByteBuf (network sync)
streamReaderByteStreamDecoder<T>Read objects from FriendlyByteBuf (network sync)
dataWriterDataEncoder<T>Encode objects to Data objects (persistence)
dataReaderDataDecoder<T>Decode objects from Data objects (persistence)

Features:

  • FastUtil-backed registry — internal Reference2ReferenceOpenHashMap for type-to-codec mapping, O(1) identity-keyed lookup
  • Multi-source construction — of(streamCodec) / of(dataCodec) / of(streamCodec, dataCodec) / of(streamCodec, mojangCodec)
  • Auto-generated enums — all enum types auto-generate codecs on first access via ConcurrentHashMapCache
  • Auto-generated arrays — all non-primitive array types auto-generate codecs on first access via ConcurrentHashMapCache
  • Generic support — register() accepts Class<?>... genericTypes, using identityHashCode-wrapped arrays as cache keys
  • Minecraft integration — register(type, Registry) convenience method auto-creates codecs from Minecraft registries

FieldDataCodec — POJO Codec

FieldDataCodec<T> wraps an annotated POJO class, serializing all its @SaveToDisk/@SyncToClient fields as a single unit. It implements both ByteStreamCodec<T> and DataCodec<T>, so it can be referenced directly in the @Codec annotation.

private static final FieldDataCodec<MyConfig> CONFIG_CODEC =
    FieldDataManager.createCodec(MyConfig.class, MyConfig::new);

@SaveToDisk
@SyncToClient
@Codec(saveCodec = "CONFIG_CODEC", syncCodec = "CONFIG_CODEC")
private MyConfig config = new MyConfig();

Internally, FieldDataCodec implements IFieldDataHolder and uses a ThreadLocal to expose the current POJO instance to its internal FieldDataManager during encode/decode. All annotated fields are serialized via writeAllToData() / readAllFromData().

Creation:

// Simple
FieldDataCodec<MyObj> codec = FieldDataManager.createCodec(MyObj.class, MyObj::new);

// With extra custom data
FieldDataCodec<MyObj> codec = FieldDataManager.createCodec(
    MyObj.class, MyObj::new,
    extraStreamWriter, extraStreamReader,   // network custom data
    extraDataWriter, extraDataReader        // disk custom data
);

DataComponent System

The DataComponent system provides an optional component-based data model, similar to vanilla Minecraft's DataComponents. It manages typed keys via DataComponentRegistry and stores data in DataComponentMap, with efficient merge semantics.

DataComponentRegistry

Extends Registry<String, DataComponentKey<?>> and simultaneously implements ByteStreamCodec<DataComponentMap>, DataCodec<DataComponentMap>, and Mojang's Codec<DataComponentMap> — usable directly as a codec for all three serialization paths.

// Create registry
DataComponentRegistry registry = new DataComponentRegistry("my_mod");
registry.unfreeze();

// Register component keys — method 1: direct codec
var ENERGY = registry.register("energy", DataSyncCodec.INT_CODEC);

// Register component keys — method 2: Builder pattern (with merge/create functions)
var ITEMS = registry.register("items", DataComponentKey
    .collectionBuilder((ArrayList<ItemStack> c) -> new ArrayList<>(c))
    .andThen(b -> b.codec(DataSyncCodec.ITEM_STACK_CODEC)));

registry.freeze();

DataComponentKey<T>

Component key with identityHashCode-based lookup. Core fields:

  • name — component name
  • codec — DataSyncCodec; when null the key does not participate in direct serialization (but still participates in merging)
  • mixCode — HashCommon.mix(System.identityHashCode(this)) — precomputed hash for identity-keyed lookup
  • mergeFunction(T oldVal, T newVal) → T — merge strategy (e.g. collection union, map putAll)
  • createFunction(T val) → T — pre-store transformation (e.g. creating a defensive copy)

Provides 100+ static Builder factory methods covering all FastUtil collection and map types with merge/create strategies.

DataComponentMap

Extends AbstractDataComponentMap, a custom hash table based on identity keys. Provides type-safe access methods:

DataComponentMap map = new DataComponentMap();
map.put(ENERGY, 1000);

// Type-safe access
int e = map.getInt(ENERGY);         // returns 0 if absent
Integer e2 = map.getData(ENERGY);    // returns null if absent
boolean has = map.containsKey(ENERGY);

// Advanced operations
map.getOrCreateData(ITEMS, ArrayList::new);  // lazy creation
map.getOrPut(ENERGY, 500);                // put if absent
map.merge(ENERGY, 200);                     // merge using key's mergeFunction
map.merge(otherMap);                           // bulk merge another map

Also provides getBoolean, getLong, getString and other typed convenience methods that return safe defaults when the key is absent.

AbstractDataComponentMap

A custom identity-based hash table base class that overrides Reference2ObjectOpenHashMap's get/put/containsKey to use DataComponentKey.mixCode (precomputed from System.identityHashCode) and == identity comparison. Key performance characteristics:

  • Identity-keyed lookup — keys with the same name in different registries have different identities, avoiding naming collisions and equals() overhead
  • Direct internal array access — bypasses FastUtil's standard API, operating directly on key[] and value[] internal arrays, eliminating method call overhead
  • Precomputed mixCode — DataComponentKey precomputes its hash via HashCommon.mix(System.identityHashCode(this)) at construction time, avoiding recalculation on each lookup
  • Open addressing — linear probing for hash collision resolution, memory-contiguous and CPU-cache-friendly

NbtUtil — NBT Conversion (v26.7.3 Revamp)

NbtUtil provides NBT ↔ Data conversion, with 3 CustomData.Type registrations. However, conversion is generally discouraged — use CustomData wrapping instead for zero-copy performance.

⚠️ Recommendation: Prefer CustomData over convertToXxx
CustomData wraps the original NBT object directly (zero-copy), while convertToData/convertToTag recursively convert the entire tree, allocating new objects — O(n) time and memory.
Only use convertToData when importing existing NBT data into the Data type system; only use convertToTag when you explicitly need NBT output from Data.

CustomData Type Registrations (Recommended)

ConstantIDWrapsNotes
TAG_TYPE0TagGeneric NBT — 1-byte type ID prefix, dispatches on read
COMPOUND_TAG_TYPE1CompoundTagKnown type — no ID prefix, more compact
LIST_TAG_TYPE2ListTagKnown type — no ID prefix, more compact
 
// ✅ Recommended: CustomData zero-copy wrapping
Data data = NbtUtil.COMPOUND_TAG_TYPE.create(tag.copy());

// ❌ Discouraged: full conversion (recursively allocates new objects)
Data data = NbtUtil.convertToData(tag);

Bidirectional Conversion (use only when necessary)

// NBT → Data (generally safe — all 13 NBT types have a Data equivalent)
Data data = NbtUtil.convertToData(compoundTag);
// Data → NBT (limited — Data has 19 types, NBT only has 13)
Tag tag = NbtUtil.convertToTag(data);

Data → NBT Conversion Limitations

NBT has 13 types while Data has 19. The following 4 Data types cannot be converted back to NBT and will throw MatchException:

  • DataMapData (ID 16) — NBT has no Data→Data map
  • IntMapData (ID 17) — NBT has no Int→Data map
  • LongMapData (ID 18) — NBT has no Long→Data map
  • CustomData (ID 15) — user-defined types, NBT cannot represent

Fully-supported bidirectional types: EndTag↔NullData, ByteTag↔ByteData, ShortTag↔ShortData, IntTag↔IntData, LongTag↔LongData, FloatTag↔FloatData, DoubleTag↔DoubleData, StringTag↔StringData, ByteArrayTag↔ByteArrayData, IntArrayTag↔IntArrayData, LongArrayTag↔LongArrayData, ListTag↔ListData (element-by-element), CompoundTag↔StringMapData (entry-by-entry).

BlockEntity Usage (Recommended)

See TestBlockEntity (in com.gto.datasynclib.test) for a complete example.

public class MyMachineBlockEntity extends FieldDataHolderBlockEntity {

    @SyncToClient(notifyUpdate = true)
    @SaveToDisk
    private int progress;

    @SyncToClient
    @SaveToDisk(defaultValue = "0")
    private int maxProgress = 100;

    @SyncToServer
    private boolean redstoneMode;

    @SaveToDisk
    private final ItemStack[] inventory = new ItemStack[9];

    public MyMachineBlockEntity(BlockPos pos, BlockState state) {
        super(ModBlockEntities.MY_MACHINE.get(), pos, state);
    }

    // Server tick (bind in your Block's getTicker)
    public void serverTick(ServerLevel level) {
        if (progress < maxProgress) {
            progress++;
            setChanged();  // ★ Mark for disk save
        }
        // Sync to client every 20 ticks
        if (level.getGameTime() % 20 == 0) {
            DataSyncNetwork.syncBlockEntityToClient(this, false, true);
        }
    }

    // Client tick
    public void clientTick() {
        if (level.getGameTime() % 20 == 0) {
            // Push redstoneMode changes to server
            DataSyncNetwork.syncBlockEntityToServer(this, false, true);
        }
    }
}

Auto Sync Explained

Network sync requires two steps working together:

  1. Annotation configuration — with autoUpdate = true (default), the framework auto-compares old and new values to detect changes; set to false to require manual markFieldsForSync("fieldName")
  2. Trigger sync explicitly — call DataSyncNetwork.syncBlockEntityToClient(be, writeAll, autoOnly) to trigger the actual network send
// autoUpdate = true (default) — automatic change detection
@SyncToClient
private int energy;

public void serverTick(ServerLevel level) {
    energy += 10;  // direct modification, framework auto-detects the change
    if (level.getGameTime() % 20 == 0) {
        DataSyncNetwork.syncBlockEntityToClient(this, false, true);
        // ↑ autoOnly=true: only checks autoUpdate fields. Internally calls updateFieldDirtyFlags(LogicalSide.SERVER, true)
        //    detectChange auto-discovers energy change → included in sync
    }
}
// autoUpdate = false — manual marking required
@SyncToClient(autoUpdate = false)
private int energy;

public void setEnergy(int value) {
    this.energy = value;
    markFieldsForSync("energy");  // ★ Must manually mark
}

Persistence Explained

Persistence relies on Minecraft's vanilla chunk save mechanism:

  1. Mark dirty chunk — call setChanged() after data changes
  2. Minecraft auto-saves — vanilla periodically checks dirty chunks and calls saveAdditional()
  3. Framework serializes — FieldDataHolderBlockEntity.saveAdditional() auto-calls writeToData()
Critical: without calling setChanged(), data will not be written to disk. Call it immediately after modifying any @SaveToDisk field.
